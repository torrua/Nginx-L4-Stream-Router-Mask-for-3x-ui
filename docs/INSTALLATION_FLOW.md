# Поток установки

`install.sh` и `setup.sh` собираются из одного сценария. Express задаёт значения по умолчанию; Expert показывает подробный опросник. Установка и проверка результата у них общие.

## Порядок действий

1. Обработать аргументы и загрузить сохранённую конфигурацию.
2. Собрать параметры выбранных компонентов. На этом этапе пакеты и службы не устанавливаются.
3. Проверить домены, диапазон портов, пересечения TCP/UDP и занятость портов сторонними службами.
4. Показать состав, порядок этапов и порты. В интерактивном режиме получить подтверждение; `--non-interactive` означает применение переданных настроек без вопросов.
5. Сохранить конфигурацию и выполнить этапы по зависимостям.
6. Проверить все выбранные службы, слушающие порты и HTTPS.
7. Сохранить завершение и вывести доступы и статистику.

Базовый план: `packages → kernel → security?`. Веб-стек добавляет `nginx → certificates → decoy → nginx_config → firewall → panel? → adguard?`. Автономный сервер добавляет `awg`. Последним всегда идёт `verify`.

Панель включается при `AUTO_SETUP_3XUI=y`; AdGuard — при `ENABLE_AGH=y` вместе с веб-стеком. Автономному AWG не требуются домен для веб-сайта, Nginx, сертификаты или 3X-UI.

При автоматической настройке 3X-UI создание API-ключа ноды включено по умолчанию. Отключить его можно ответом «Нет», параметром `--no-node-token` или `ENABLE_NODE_TOKEN=n`. Действующий сохранённый ключ используется повторно; новый создаётся, если сохранённый ключ отсутствует или недействителен. Сам ключ передаётся основному установщику, выводится в итогах и сохраняется в `/root/vpn_credentials.txt` и конфигурации с правами `600`. Ошибка создания или передачи ключа останавливает этап настройки панели.

## Ошибки, диагностика и возобновление

Обязательный этап нельзя засчитать выполненным после ошибки. Исполнитель предлагает повторить действие или прервать установку; пропуск отсутствует. В обычном режиме, `--debug` и при вызове из условия действует одинаковая обработка ошибок. Задачи запускаются в отдельном Bash с копией функций и переменных; изменения переменных дочерней задачи не возвращаются в родительский процесс.

**Умная диагностика при сбоях (Smart Silent Debug):** В штатном режиме вывод шагов буферизуется, в терминале отображаются лаконичные спиннеры. При возникновении ошибки на любом этапе скрипт автоматически перехватывает и выводит полный лог сбойной команды, статус соответствующих systemd-служб и рекомендации по устранению (ручной перезапуск с `--debug` не требуется).

**Явный режим отладки (`--debug` / `DEBUG_MODE=1`):** Отключает спиннеры, выводит весь поток команд напрямую в stdout/stderr с временными метками `=== START TASK ===` и `=== END TASK ===`, активирует ловушку `[ERROR-TRACE]` и сохраняет полный системный протокол в `/var/log/server-setup.log`. При запуске через `curl | bash` флаги передаются через `curl ... | sudo bash -s -- --debug`.

**Аудит и сухой прогон (`--check` и `--dry-run`):**
* В установщике `setup.sh` неразрушающий аудит запускается ключом `--check` (или `--doctor`): диагностирует ОС, порты, SSL и защиту от сканеров Censys без внесения изменений в систему.
* В утилите обслуживания `maintain.sh` и конфигураторе `configure-panel.sh` реализован режим `--dry-run`: выполняет полный аудит базы SQLite 3X-UI, шаблона Xray и правил Nginx без сохранения транзакции и без перезапуска служб. Выгрузить отчет аудита в файл без ANSI-кодов: `./maintain.sh --dry-run | sed 's/\x1b\[[0-9;]*m//g' > audit.log`.

Ошибки выпуска сертификата останавливают установку. Самоподписанный сертификат автоматически не подставляется. Провал итоговой проверки возвращает ненулевой код и блокирует сообщение об успешном завершении.

Конфигурация хранится в `server-setup.env` либо явно переданном файле. Имена `setup_mask.env` поддерживаются. Рядом создаётся `<имя-конфига>.state` с правами `600`: устойчивые имена этапов, подписи их параметров и последний завершённый этап. Состояние записывается атомарно и не содержит исходных значений секретов.

При возобновлении этап пропускается только при совпадении подписи и наличии проверяемого результата. `verify` выполняется всегда; безопасность и firewall применяются повторно. Старые числовые контрольные точки без подписей не используются для пропуска этапов. `--rotate-paths` принудительно запускает план с начала.

## Снимок состояния и деинсталляция (`uninstall.sh`)

Перед началом внесения любых изменений модуль `src/system/snapshot.sh` создает моментальный снимок начального состояния сервера в `/var/backups/server_setup/snapshot_initial/` (правила UFW, sysctl, SSH, DNS resolv.conf, cron-задачи, список активных служб).

Для полного отката системы и возврата сервера к исходному состоянию используется инструмент `uninstall.sh`:
* Восстанавливает исходные настройки UFW, sysctl и SSH (с обязательной проверкой Anti-Lockout для предотвращения блокировки доступа администратора).
* Останавливает и удаляет установленные службы (3X-UI, Nginx, AdGuard Home, AmneziaWG DKMS, Docker-контейнеры).
* Предлагает интерактивный выбор: сохранить или удалить SSL-сертификаты (Let's Encrypt / ACME Cloudflare). В неинтерактивном режиме поведение регулируется флагами `--keep-certs` (по умолчанию) или `--remove-certs`.
* Очищает системные переопределения `systemd-resolved` и фоновые cron-задачи автообновления/самовосстановления.

## Ответственность модулей

| Модуль | Назначение |
| --- | --- |
| `src/entrypoints/setup.main.sh` | Общий порядок загрузки и запуска |
| `src/entrypoints/maintain.main.sh` | Точка входа утилиты обслуживания, бэкапа и аудита maintain.sh |
| `src/entrypoints/uninstall.main.sh` | Точка входа деинсталлятора и полного отката системы |
| `src/common/backup.sh` | Транзакционный бэкап, WAL-safe снимки SQLite, валидация SSL и безопасный откат |
| `src/system/snapshot.sh` | Создание и проверка исходного снимка конфигураций сервера |
| `src/system/uninstall.sh` | Логика отката, очистки сервисов, сертификатов и cron |
| `src/panel/configure.sh` | Автономный запуск и интеграция реконсиляции базы 3X-UI |
| `src/panel/reconcile.py` | Модуль инбаундов 3X-UI, роутинга Xray и экспорта клиентов |
| `diagnostics/mtr-backend.py` | Демон сетевой диагностики MTR и Speedtest через Unix-сокет |
| `src/tui/wizard.sh` | Опрос и редактирование параметров |
| `src/installer/express.sh` | Пресет с сохранением явно заданных параметров |
| `src/installer/plan.sh` | Построение, показ, валидация и выполнение плана |
| `src/common/protocols.sh` | Список портов выбранных протоколов для плана и проверки |
| `src/common/checkpoint.sh` | Подписи и возобновление этапов |
| `src/common/spinner.sh` | Выполнение задач, умная буферизация логов и повтор при ошибке |
| `src/installer/engine.sh` | Реализация этапов и подключение модулей компонентов |
| `src/installer/report*.sh` | Итоговые доступы и статистика после проверки |

## Проверка изменений

```bash
python scripts/build.py --lint
python scripts/build.py --check --lint
pytest tests/
```

Тестовый сьют (`pytest tests/`, 184 теста) проверяет планы компонентов, остановку после ошибки, отмену до применения, контрольные точки, сохранение Express-параметров, конфликты портов, жизненный цикл API-токенов ноды, деинсталляцию и откат (`test_uninstall.py`), синтаксическую корректность AST панели (`test_panel_refactor.py`) и обратную совместимость оберток. Сквозные проверки используют настоящий CLI и мастер обоих входных скриптов с подменой системных операций; они не устанавливают службы на хосте. Полную установку и повторный запуск следует дополнительно проверять на отдельной Ubuntu/Debian VM.
