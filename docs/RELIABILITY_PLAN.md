# План повышения надёжности установщика

Документ для передачи исполнителю. Задача — сделать установку, повторное применение настроек, обновление, восстановление и удаление предсказуемыми и проверяемыми.

Это план работ, а не утверждение о готовности перечисленных возможностей. Выполнение каждой задачи подтверждается артефактами проверки.

Редакция 2 от 2026-10-21. Аудит плана выполнен по текущему рабочему дереву. Сохранены идентификаторы T00–T26; добавлены T27–T30. Состояние реализации не выводится из названия релиза или наличия теста: у каждого критерия ниже начальный статус «не принято» до предъявления доказательств.

## 1. Исходное состояние и обязательные ограничения

- На момент повторного аудита VERSION содержит v9.2.0; HEAD — 78e19f2. Изменение версии, документация релиза и существенная часть исправлений находятся в незакоммиченном рабочем дереве, включая diagnostics/, docs/RELEASE_NOTES_v9.2.0.md и tests/test_audit_v91_fixes.py. Это не подтверждение опубликованного или испытанного релиза. Перед началом реализации повторно снять состояние по T00.
- Сохранить все текущие изменения. Не применять reset/clean и не заменять рабочее дерево содержимым тега v9.1.0.
- Не использовать DevRelay: инструменты, навыки, поиск, публикации и сохранение сессий. Это явное предпочтение пользователя.
- Основные скрипты: install.sh, setup.sh, configure-panel.sh, maintain.sh, prepare-server.sh, manage-services.sh, uninstall.sh. Сохранить нейтральное именование.
- Shell-реализацию изменять в src/; генерируемые корневые скрипты обновлять через scripts/build.py. diagnostics/, scripts/, tests/, compose/ и CI имеют собственные исходники и изменяются непосредственно. Не править сгенерированные копии вместо источников.
- Сохранить Express/Expert, существующие параметры CLI, старые конфигурации, возобновление установки и автономный AWG без обязательного веб-стека.
- Сохранить стрелочный мультивыбор, включая задержки передачи ESC-последовательностей через SSH.
- Создание API-ключа ноды 3X-UI остаётся включённым по умолчанию. Явное «Нет» сохраняется. Действующий ключ не ротируется без необходимости; сам ключ выводится в итогах и сохраняется в защищённом файле доступов.
- Рабочие VPS, реальные домены и рабочие секреты пользователя не использовать для автоматических тестов. Испытания проводить на выделенных VM с тестовыми данными.
- Не переписывать проект целиком на другой язык. Bash можно оставить для оркестрации; структурированные данные и сложные файловые операции выделять в небольшие тестируемые модули.
- Не удалять протоколы или существующие возможности ради прохождения тестов. Непроверенные сочетания явно обозначать в матрице поддержки.

Все пути далее указаны относительно корня репозитория.

## 2. Приоритеты и правила приёмки

- P0: безопасность данных, воспроизводимость релиза и доказательство работоспособности.
- P1: полный жизненный цикл компонентов, управление ОС, изоляция и восстановление.
- P2: удобство сопровождения, документация и завершение эксплуатационных процедур.

Для каждой задачи исполнитель предоставляет: перечень изменений, команды проверки, ожидаемый и фактический результат, ограничения и ссылки на артефакты. «Тесты прошли» без описания проверяемого поведения недостаточно.

Для опасных операций нужны поведенческие тесты с отказами. Проверки наличия строк допустимы для формата сборки, но не доказывают безопасность отката, авторизацию или сохранность данных.

**Два разных результата тестовой задачи.** T02/T03 сначала создают исполняемые сценарии и фиксируют исходные сбои. Это позволяет начать исправления; наличие такого стенда не означает приёмку поведения. Критерии этих задач закрываются только после успешного повторного прогона на итоговой версии. Исправления не зависят от предварительного успеха тестов, которые они должны исправить.

**Доказательство для каждого критерия:** идентификатор Txx.Cyy, снимок исходников/commit, ОС и версии зависимостей, точная команда, код завершения, ожидаемое и фактическое состояние, очищенный от секретов артефакт. Пропуск теста, неподготовленный стенд и недоступная внешняя зависимость дают статус «не проверено», а не «принято». Подтверждение получения ресурса по HTTP не заменяет клиентское подключение нужного протокола.

**Граница чтения.** Для --check/--dry-run разрешены документированные сетевые пробы и ограниченные временные файлы вне управляемой конфигурации. Не меняются пакеты, службы, firewall, конфигурации, БД и её WAL/SHM, checkpoint и ключи. Системные журналы ОС могут фиксировать обращения. Явный --gen-config записывает только запрошенный файл и не считается режимом чистого чтения. --debug меняет детализацию вывода и сам по себе не запрещает применение.

**Граница объёма.** Первый этап охватывает существующие режимы проекта на Ubuntu 24.04 amd64; перенос на другой язык, новый оркестратор, новые протоколы и универсальная система управления серверами не требуются. Для T23 достаточно одного документированного внешнего хранилища и одного поддерживаемого формата шифрования. Известные ограничения не снимают требований сохранности данных и доступа.

## 5. Безопасное применение изменений

### T07. Заблокировать параллельные изменяющие операции

Приоритет: P0. Зависимости: T00.

Работы: общая межпроцессная блокировка всех операций, меняющих управляемое состояние, включая prepare-server, configure-panel, manage-services, менеджеры клиентов, backup/restore, uninstall и фоновые задания проекта.

Приёмка:

- [ ] **T07.C01** Два изменяющих запуска не могут одновременно работать с одним серверным состоянием.
- [ ] **T07.C02** Второй процесс сообщает владельца блокировки и ожидает ограниченное время либо завершается с понятным кодом.
- [ ] **T07.C03** Блокировка сохраняется, пока владелец или его дочерние процессы меняют состояние. После прекращения всей операции она освобождается; гибель только родителя не допускает второй запуск одновременно с продолжающим запись потомком.
- [ ] **T07.C04** Дескриптор блокировки не остаётся у запущенных постоянных служб.
- [ ] **T07.C05** Диагностические команды чтения имеют документированное поведение при активной операции.
- [ ] **T07.C06** Проверены пары install/install, install/restore, maintain/uninstall.
- [ ] **T07.C07** Проверены backup/restore, backup/update, менеджер клиентов/restore и вложенный install → setup. Вложенный запуск не блокирует сам себя; локальный непривилегированный процесс не может подменить путь lock-файла ссылкой.
- [ ] **T07.C08** Блокировка shell-команд не выдаётся за блокировку записей работающей панели в SQLite: согласованность БД и конфигурации отдельно обеспечивается T21.

Приёмка:

## 14. Порядок выполнения и контрольные точки

1. Выполнить T00; сохранить исходные материалы и результаты.
2. Создать фундамент: T01, T04, T07, T13, T14; включить быстрый CI из T25. Создать исходные сценарии T02/T03 и сохранить сбои до рефакторинга.
3. Подключать задачи по указанным зависимостям: сначала доверие к релизу T05/T06, CLI T29, ошибки T09, безопасный бэкап T21 и диагностику T18–T20; затем T10/T15/T16, журнал T08 и зависимые SSH/restore. Приоритет P0 определяет срочность результата: необходимые зависимости P1 выполнять раньше зависимых задач P0. Независимые исправления не откладывать до завершения всего реестра ресурсов.
4. После каждого изменения повторять относящиеся к нему проверки; полный набор — после завершения этапа и перед итоговой приёмкой.
5. Отдельно проверить конфигурацию, в которой функции отключены: отсутствие компонента не должно ломать установку и отчёт.
6. Завершить T26 только после проверки всей обязательной матрицы. Невыполненные пункты перечислить явно.

В журнале задач различать: не начато, выполняется, реализовано без приёмки, принято, заблокировано с причиной.

- **G0 — зафиксированная исходная точка:** T00/T01 приняты, сценарии T02/T03 исполняются, исходные сбои перечислены. Это разрешает работу над исправлениями, но не выпуск.
- **G1 — устранены критические риски:** все критерии P0 и необходимые зависимости приняты; относящиеся к ним A-сценарии проходят на точном снимке результата. Эта отметка не означает завершения всего плана и не обещает внешний disaster recovery до T23.
- **G2 — выполнен весь план:** все T00–T30 приняты, все A01–A28 пройдены, полная VM-матрица и релизные проверки T25 выполнены; T26 содержит итоговый отчёт. Непроверенная платформа/сочетание явно исключены из обещанной поддержки.

Для G1/G2 допускается заранее документировать неприменимость сценария только к конкретному профилю (например, ACME для автономного AWG). Обязательный сценарий не пропускается целиком из-за трудности реализации. Если нет VM/гипервизора, исполнитель выполняет независимые задачи и оставляет зависимые критерии непроверенными; контейнерный --help не заменяет системные испытания.
